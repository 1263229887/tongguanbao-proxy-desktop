# 关务前置机对接接口文档

> 版本：v1.3
>
> 更新时间：2026-09-17
>
> 适用对象：Windows 前置机开发、测试和部署人员
>
> 对接范围：前置机从本项目拉取单一窗口暂存任务，将 DEC XML 投递到本地 OutBox，并将 InBox 暂存回执上传给本项目

## 1. 对接范围与术语

本项目提供 HTTP 接口，不负责开发、安装或运维 Windows 前置机。前置机负责连接本项目与客户机上的单一窗口客户端目录。

```text
本项目后端
  -> 前置机拉取任务
  -> 前置机将 DEC XML 原子写入统一 OutBox
  -> 单一窗口客户端取走文件并产生 InBox 回执
  -> 前置机将回执原文上传本项目
  -> 本项目解析回执并更新暂存状态
```

本文中的关键状态含义：

| 状态/结果 | 准确定义 |
|---|---|
| `OUTBOX_DROPPED` | 前置机已把 DEC XML 成功放入单一窗口客户端的 OutBox。`DROPPED` 表示“投递完成”，不是“丢弃”。 |
| `RECEIPT_PENDING` | 后端已确认文件进入 OutBox，正在等待暂存回执。 |
| `SUCCESS` | 后端收到白名单内的暂存回执，且 `ResponseCode = 0`。只表示当前“单一暂存”成功，不表示最终申报、审结或放行成功。 |
| `FAILED` | 后端收到的暂存回执 `ResponseCode != 0`。 |
| `DELIVERY_UNKNOWN` | 分派租约已过期，但后端无法确认文件是否已进入 OutBox，必须人工核实。 |

租户类型和识别制单时的企业字段默认填充属于业务前端逻辑，与前置机、Python 解析及本文接口无关。

## 2. 对接前置条件

联调前由双方确认以下条件：

| 条件 | 责任方 |
|---|---|
| 提供测试/生产环境 HTTPS 基础地址 | 本项目 |
| 开启后端前置机总开关 | 本项目 |
| 为租户生成并安全交付企业鉴权密钥 `sk-...` | 本项目 |
| 确认前置机可访问后端 HTTPS 地址 | 前置机/客户网络 |
| 确认单一窗口客户端的统一 OutBox、InBox 目录 | 前置机/客户现场 |
| 配置稳定且唯一的 `instanceName`，例如 `WH-SH-01` | 前置机 |
| 保证 Windows 主机时间准确，建议启用 NTP | 前置机/客户现场 |

建议的本地配置结构：

```yaml
server:
  base-url: https://api.example.com
  agent-key: sk-replace-with-tenant-enterprise-key

instance:
  name: WH-SH-01

customs:
  supported-trade-modes: [export, import, "9610"]
  outbox: D:\\Deccus001\\OutBox
  inbox: D:\\Deccus001\\InBox

ledger:
  path: data\\delivery-ledger.db

poll:
  task-interval: 10s
  inbox-interval: 3s
  heartbeat-interval: 30s
```

以上目录仅为示例，现场必须以实际单一窗口客户端配置为准。出口、进口和 `9610` DEC 统一写入同一个 OutBox；单一窗口依据 DEC 内的 `DecHead.IEFlag`（`I` 进口、`E` 出口）识别进出口，不需要维护 `tradeMode -> 目录` 映射。前置机不得移动或删除 InBox 中的回执文件，历史文件由客户现场自行维护。

## 3. 认证与公共协议

### 3.1 基础约定

| 项目 | 约定 |
|---|---|
| 接口前缀 | `/admin-api/declaration/agent` |
| 协议 | 生产环境必须使用 HTTPS |
| 方法 | 全部为 `POST` |
| 请求类型 | `Content-Type: application/json` |
| 认证请求头 | `X-Agent-Key: sk-...` |
| 日期时间格式 | `yyyy-MM-dd HH:mm:ss`，例如 `2026-09-14 15:32:11` |
| 字符编码 | UTF-8 |

每次请求都必须携带：

```http
Content-Type: application/json
X-Agent-Key: sk-tenant-enterprise-key
```

`X-Agent-Key` 是本项目为某个租户签发的企业鉴权密钥。前置机不需要发送登录 Token、租户 ID 或用户 ID；后端根据密钥识别租户并进行数据隔离。

特别说明：`DANA_ENTERPRISE_KEY_SECRET` 是本项目后端服务器用于保护企业密钥的主密钥，只能配置在后端服务器环境中，绝不能下发、写入或发送给前置机。前置机只保存 `sk-...` 企业鉴权密钥。

### 3.2 公共响应结构

成功响应：

```json
{
  "code": 0,
  "msg": "",
  "data": {}
}
```

失败响应：

```json
{
  "code": 1050000201,
  "msg": "企业鉴权密钥无效",
  "data": null
}
```

前置机必须同时判断 HTTP 状态码和响应体 `code`：

- 只有 `2xx` 且 `code = 0` 才是接口调用成功。
- 鉴权拦截失败会明确返回 HTTP `401` 或 `503`。
- DTO 校验和普通业务错误通常仍使用公共 JSON 响应，不能只根据 HTTP `200` 判断成功。
- 响应无法解析、连接中断或超时均视为结果未知，按本文重试规则处理。

| 接口 | 路径 | 用途 |
|---|---|---|
| 拉取任务 | `POST /tasks/pull` | 拉取待投递的 DEC XML |
| 回报投递状态 | `POST /tasks/{taskId}/status` | 告知后端 OutBox 投递成功或失败 |
| 上传回执 | `POST /receipts` | 原样上传单一窗口 InBox XML |

## 5. 拉取任务

### 5.1 请求

```http
POST /admin-api/declaration/agent/tasks/pull
```

```json
{
  "instanceName": "WH-SH-01",
  "tradeModes": ["export", "import", "9610"],
  "batchSize": 5
}
```

| 字段 | 必填 | 约束 | 说明 |
|---|---|---|---|
| `instanceName` | 是 | 非空，最长 64 | 本机稳定实例名；重启后不得随机变化。 |
| `tradeModes` | 是 | 非空数组；元素只能为 `export`、`import`、`9610` | 本实例允许拉取的任务类型，用于服务端过滤，不用于选择本地目录。 |
| `batchSize` | 否 | 1～100 | 省略时默认为 5；服务端当前实际封顶 20。 |

### 5.2 响应

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "tasks": [
      {
        "taskId": 33,
        "orderId": 68,
        "tradeMode": "export",
        "businessModuleCode": "DECCUS001",
        "clientSeqNo": "202609141530000123",
        "fileName": "DEC报关单_EXPORT_20260904160012_3764.xml",
        "xmlSha256": "ab3d7f0d0cdb...",
        "dispatchToken": "bb4635d4-0dc4-4ec8-8f33-8f9b7b650662",
        "leaseExpireAt": "2026-09-14 15:40:00",
        "decXmlBase64": "PD94bWwgdmVyc2lvbj0iMS4wIiBlbmNvZGluZz0iVVRGLTgiPz4..."
      }
    ]
  }
}
```

没有可用任务时返回空数组：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "tasks": []
  }
}
```

| 响应字段 | 说明 |
|---|---|
| `taskId` | 前置机任务标识，也是后续状态回报路径参数。 |
| `orderId` | 本项目业务订单标识，只用于排障和审计。 |
| `tradeMode` | 后端任务分类和审计字段，不决定本地目录；所有 DEC 均写入统一 OutBox。 |
| `businessModuleCode` | 前置机业务模块代码。当前单一窗口报关单暂存固定为 `DECCUS001`，用于选择“货物申报（报关单暂存）”模块。 |
| `clientSeqNo` | 后端生成的单一窗口业务流水号，前置机不得修改或自行生成。 |
| `fileName` | 后端指定的目标文件名。 |
| `xmlSha256` | DEC XML 原始字节的 SHA-256 小写十六进制值，用于本地投递防重。 |
| `dispatchToken` | 本次分派唯一令牌，状态回报必须原样带回。 |
| `leaseExpireAt` | 本次分派租约到期时间，默认租期 10 分钟。 |
| `decXmlBase64` | 完整 DEC XML 的 Base64。解码后按原始字节写盘，不得转码或重排 XML。 |

当前单一暂存 DEC 报文的关键字段口径如下。前置机只负责原样投递，不得修改这些字段：

| DEC 字段 | 业务含义 | 当前值来源 |
|---|---|---|
| `DecSign.OperType` | 操作类型 | 固定为 `G`，表示报关单暂存，不是正式申报 `C`。 |
| `DecHead.IEFlag` | 进出口标志 | `I` 表示进口，`E` 表示出口；单一窗口据此识别进出口。 |
| `DecHead.AgentCode` | 申报单位代码 | 草稿交易信息中的申报单位代码。 |
| `DecHead.AgentName` | 申报单位名称 | 草稿交易信息中的申报单位名称。 |
| `DecHead.CopCode` | 录入单位代码 | 草稿交易信息中的录入单位代码。 |
| `DecHead.CopName` | 录入单位名称 | 草稿交易信息中的录入单位名称。 |
| `DecSign.CopCode` | 录入单位代码 | 与 `DecHead.CopCode` 使用同一录入单位代码。 |

拉取成功后，后端已经将任务从 `READY` 原子更新为 `DISPATCHED`。每次分派都会生成新的 `dispatchToken` 和租约。

前置机业务模块代码以其产品配置为准，当前已知对应关系如下：

| 业务模块 | 代码 |
|---|---|
| 默认 | `OTHERS` |
| 报关代理委托申报 | `ACD` |
| 跨境电商进口 | `IMPCEB` |
| 跨境电商出口 | `EXPCEB` |
| 货物申报（报关单暂存） | `DECCUS001` |
| 海运/空运舱单申报 | `MFT` |
| 报关单修撤 | `DECCUS102` |

本项目当前只下发 `DECCUS001`。`export`、`import`、`9610` 是本项目的任务分类，不是业务模块代码；即使 `tradeMode=9610`，当前生成和投递的仍是 DEC 4.8 报关单暂存报文，因此业务模块仍为 `DECCUS001`。前置机收到自身不支持的 `businessModuleCode` 时必须停止投递并告警，不得自动回退到 `OTHERS`。

### 5.3 前置机处理要求

每个任务必须按以下顺序处理：

1. 校验 `businessModuleCode=DECCUS001`，并检查该模块统一 OutBox 配置及写权限；所有 `tradeMode` 的 DEC 均写入该目录，前置机不得修改 XML 内的 `IEFlag`。
2. 以 `taskId + xmlSha256` 查询 SQLite 投递账本/写前日志。
3. 账本已存在 `DELIVERED` 记录时，不得再次写 OutBox；直接使用本次新的 `dispatchToken` 回报 `OUTBOX_DROPPED`。
4. 账本中同一 `taskId` 已存在但 `xmlSha256` 不同时，停止处理并人工告警，不得覆盖旧文件。
5. Base64 解码后可复算 SHA-256；不一致时不得写盘，回报 `FAILED`。
6. 参考心跳返回的服务器时间校正本地比较，在写临时文件前检查 `leaseExpireAt`。
7. 在目标 OutBox 同盘写入临时文件，例如 `.filename.xml.taskId.tmp`，写完后 flush 并关闭文件。
8. 原子 rename 前再次检查租约；租约已过期时删除临时文件，不得产生正式 OutBox 文件，也不要回报 `FAILED`，应记录告警等待人工裁决。
9. rename 前将 `PREPARED` 写前记录持久化并 flush 到磁盘，再原子 rename 为服务端指定的 `fileName`。若目标文件已存在，必须结合账本人工/程序判定，禁止直接覆盖。
10. rename 成功后立即将账本状态更新为 `DELIVERED` 并 flush，再回报 `OUTBOX_DROPPED`。

SQLite 与文件系统不能组成同一个原子事务，因此必须保留 `PREPARED` 写前状态。进程恢复时：正式文件存在且哈希相同，可补记 `DELIVERED`；临时文件仍存在且正式文件不存在，说明 rename 尚未执行，可删除临时文件并在租约有效时重做；临时文件和正式文件均不存在时，可能已被单一窗口客户端取走，属于投递结果不确定，禁止自动重写，等待后端任务进入 `DELIVERY_UNKNOWN` 后人工核实。

如果拉取请求的响应在网络中丢失，后端任务可能已经变为 `DISPATCHED`。前置机不得猜测任务内容；继续轮询即可，该任务租约到期后会进入 `DELIVERY_UNKNOWN`，由后端管理员人工核实，系统不会自动重投。

## 6. 回报投递状态

### 6.1 请求

```http
POST /admin-api/declaration/agent/tasks/{taskId}/status
```

成功投递：

```json
{
  "instanceName": "WH-SH-01",
  "dispatchToken": "bb4635d4-0dc4-4ec8-8f33-8f9b7b650662",
  "status": "OUTBOX_DROPPED",
  "message": "已写入统一 OutBox，投递账本已落库"
}
```

明确未投递：

```json
{
  "instanceName": "WH-SH-01",
  "dispatchToken": "bb4635d4-0dc4-4ec8-8f33-8f9b7b650662",
  "status": "FAILED",
  "message": "统一 OutBox 目录不可写"
}
```

| 字段 | 必填 | 约束 | 说明 |
|---|---|---|---|
| 路径 `taskId` | 是 | 后端返回的整数 | 必须来自本次拉取结果。 |
| `instanceName` | 是 | 非空，最长 64 | 必须与拉取任务时一致。 |
| `dispatchToken` | 是 | 非空，最长 64 | 必须使用该任务本次分派的令牌。 |
| `status` | 是 | `OUTBOX_DROPPED` 或 `FAILED` | 不接受其他值。 |
| `message` | 否 | 最长 500 | 简短说明，不得包含密钥或完整 XML。 |

成功响应：

```json
{
  "code": 0,
  "msg": "",
  "data": true
}
```

后端状态变化：

- `OUTBOX_DROPPED`：`DISPATCHED` 或令牌仍有效的 `DELIVERY_UNKNOWN` -> `RECEIPT_PENDING`。
- `FAILED`：仅允许 `DISPATCHED` -> `UPLOAD_FAILED`。
- 实例名错误、令牌过期/错误或当前状态不允许时返回 `1050000203`。

只有在“确认正式文件没有进入 OutBox”时才能回报 `FAILED`。若 rename 已成功但状态接口超时，只能重试同一个 `OUTBOX_DROPPED` 请求，绝不能改报 `FAILED`，也不能再次写文件。由于当前状态回报接口不是重复成功型接口，如果首次请求实际已被后端处理但响应丢失，重试可能返回 `1050000203`；此时保留 `DELIVERED` 账本、停止重写和重复回报，并告警供双方核查。

## 7. 上传回执

### 7.1 请求

```http
POST /admin-api/declaration/agent/receipts
```

```json
{
  "instanceName": "WH-SH-01",
  "fileName": "DecImportResponse_20260914153211.xml",
  "receivedAt": "2026-09-14 15:32:11",
  "receiptXmlBase64": "PD94bWwgdmVyc2lvbj0iMS4wIiBlbmNvZGluZz0iVVRGLTgiPz4..."
}
```

| 字段 | 必填 | 约束 | 说明 |
|---|---|---|---|
| `instanceName` | 是 | 非空，最长 64 | 当前实例名。 |
| `tradeMode` | 否 | `export`、`import` 或 `9610` | 可选核对字段。统一 InBox 无法可靠判断任务类型时应省略，后端按 XML 内的 `ClientSeqNo` 匹配任务。 |
| `fileName` | 是 | 非空，最长 255 | InBox 原始文件名。 |
| `receivedAt` | 否 | 日期时间 | 前置机发现/接收文件的时间；省略时以后端接收时间为准。 |
| `receiptXmlBase64` | 是 | Base64 文本最长 4 MiB | 回执文件原始字节的 Base64；解码后默认不得超过 3 MiB。 |

前置机不要解析或修改回执 XML，不要改变编码、换行、命名空间或元素顺序。后端会从 XML 提取 `ClientSeqNo`、`ResponseCode`、`ErrorMessage`、`SeqNo/EntryId/PreEntryId` 和回执类型。

### 7.2 响应

匹配到任务并更新状态：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": true,
    "taskId": 33,
    "customsStatus": "SUCCESS",
    "duplicate": false
  }
}
```

重复上传：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": true,
    "taskId": 33,
    "customsStatus": "SUCCESS",
    "duplicate": true
  }
}
```

未匹配到本项目任务：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "matched": false,
    "taskId": null,
    "customsStatus": null,
    "duplicate": false
  }
}
```

| 响应字段 | 说明 |
|---|---|
| `matched` | 是否按 `ClientSeqNo` 匹配到当前租户的后端任务。 |
| `taskId` | 匹配到的任务 ID；未匹配时为空。 |
| `customsStatus` | 当前任务状态，常见为 `SUCCESS` 或 `FAILED`。未知回执类型可能保持原状态。 |
| `duplicate` | 是否命中后端回执幂等记录。重复上传不会重复推进状态，但该字段不能脱离 `matched` 单独作为匹配成功依据。 |

当前首期暂存回执白名单为 `DecImportResponse`。其 `ResponseCode = "0"` 时任务进入 `SUCCESS`，其他值进入 `FAILED`。不在白名单内的后续阶段回执会被留档，但不会改变暂存主状态。

后端幂等键为“租户 + XML 内 `ClientSeqNo` + XML SHA-256”。因此同一原始回执可安全重试。

### 7.3 InBox 文件处理要求

1. 轮询统一 InBox，不按 `tradeMode` 拆分目录。
2. 仅处理已写完的 XML；建议文件大小和最后修改时间连续两次扫描保持不变后再读取。
3. 按原始字节读取并 Base64 编码，不做 XML 解析或字符集转换。
4. 前置机只读取文件，不得移动、重命名或删除 InBox 中的任何回执；客户现场负责历史文件清理和容量维护。
5. 每次读取稳定文件后计算原始字节的 SHA-256，以该值作为本地回执内容唯一标识。文件名、路径、大小和最后修改时间只作为审计信息和变化检测依据。
6. 上传结果必须持久化到本地 SQLite 回执处理账本。后续扫描命中已确认或永久拒绝的 SHA-256 时直接跳过，不再调用后端。
7. 网络异常、超时、响应无法解析或服务端临时错误时记录 `RETRY_PENDING` 并按退避策略重试；原文件始终留在 InBox。
8. 后端返回未匹配、非法 XML 或文件过大时只更新账本并告警，不移动文件，由客户或双方人工核查。

建议的本地回执处理状态：

| 本地状态 | 含义 | 后续扫描动作 |
|---|---|---|
| `PENDING` | 新发现、尚未获得后端明确响应 | 上传。 |
| `RETRY_PENDING` | 网络或后端临时异常 | 到达下次重试时间后重新上传。 |
| `ACKED_MATCHED` | 后端已接收且匹配到任务 | 直接跳过。 |
| `ACKED_UNMATCHED` | 后端已接收但未匹配到本项目任务 | 直接跳过并保留告警，等待人工核查。 |
| `PERMANENT_REJECTED` | XML/Base64 非法、缺少 `ClientSeqNo` 或文件过大 | 直接跳过并保留告警，等待客户处理文件。 |

接口响应与本地账本状态的对应关系：

| 接口结果 | 写入的本地状态 | 处理要求 |
|---|---|---|
| `2xx + code=0 + matched=true + duplicate=false` | `ACKED_MATCHED` | 首次被后端接收并匹配，后续跳过。 |
| `2xx + code=0 + matched=true + duplicate=true` | `ACKED_MATCHED` | 后端此前已接收，后续跳过。 |
| `2xx + code=0 + matched=false` | `ACKED_UNMATCHED` | 无论 `duplicate` 取值如何，均停止自动重传并告警。 |
| `1050000204` 或 `1050000205` | `PERMANENT_REJECTED` | 自动重试无法修复，停止自动重传并告警。 |
| 网络错误、响应未知或可重试的服务端错误 | `RETRY_PENDING` | 指数退避重试；不得提前记为已确认。 |

账本至少记录 `xmlSha256`、完整路径、文件名、大小、最后修改时间、本地状态、`taskId`、`customsStatus`、最后尝试时间和错误摘要。建议以 `xmlSha256` 建唯一约束：相同内容即使被复制或改名也不重复上传；同名文件内容发生变化后 SHA-256 会变化，应作为新回执处理。账本必须在接口响应处理完成时同步持久化，不能只保存在内存。客户删除 InBox 文件后，前置机可以按双方约定的保留期清理相应账本记录；文件仍存在时不得自动过期已确认记录。

`taskId` 和 `customsStatus` 仅作为后端响应和审计信息，不能用作本地文件去重键。一个任务可能存在多份不同回执，而扫描文件前也无法可靠获得 `taskId`。

## 8. 心跳

### 8.1 请求

```http
POST /admin-api/declaration/agent/heartbeat
```

```json
{
  "instanceName": "WH-SH-01",
  "ip": "172.30.16.1",
  "version": "1.0.0",
  "channelCodes": ["Shanghai"],
  "tradeModes": [
    {
      "tradeMode": "shared",
      "outboxOk": true,
      "inboxOk": false
    }
  ],
  "pendingTaskCount": 2,
  "lastError": "统一 InBox 不可读"
}
```

| 字段 | 必填 | 约束 | 说明 |
|---|---|---|---|
| `instanceName` | 是 | 非空，最长 64 | 当前实例稳定名称。 |
| `ip` | 否 | 最长 64 | 当前主机 IP。 |
| `version` | 否 | 最长 32 | 前置机版本。 |
| `channelCodes` | 否 | 字符串数组 | 当前仅用于展示，不参与任务路由。 |
| `tradeModes` | 否 | JSON 对象数组 | 兼容现有接口字段；统一目录场景上报一条 `tradeMode=shared` 的 OutBox/InBox 健康状态。 |
| `pendingTaskCount` | 否 | 整数 | 本地等待处理/回报的任务数。 |
| `lastError` | 否 | 最长 500 | 最近错误摘要，不得包含密钥或完整 XML。 |

响应：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "now": "2026-09-14 15:32:11"
  }
}
```

建议每 30～60 秒上报一次。后端当前默认超过 3 分钟未收到心跳即视为超时；每次连续离线只告警一次，恢复心跳后再次离线才产生新告警。前置机可根据响应 `now` 估算与服务器的时钟偏移，用于租约判断，但仍应同时保证操作系统时钟准确。

## 9. 状态机与异常恢复

```text
READY
  -> DISPATCHED
      -> RECEIPT_PENDING -> SUCCESS / FAILED
      -> UPLOAD_FAILED
      -> DELIVERY_UNKNOWN
```

| 状态变化 | 触发条件 |
|---|---|
| `READY -> DISPATCHED` | 前置机 pull 时后端原子抢占任务。 |
| `DISPATCHED -> RECEIPT_PENDING` | 前置机回报 `OUTBOX_DROPPED`。 |
| `DISPATCHED -> UPLOAD_FAILED` | 前置机在文件进入 OutBox 前明确失败并回报 `FAILED`。 |
| `DISPATCHED -> DELIVERY_UNKNOWN` | 租约到期仍未收到可信状态回报。 |
| 非终态 -> `SUCCESS/FAILED` | 后端收到并匹配白名单暂存回执。 |

`DELIVERY_UNKNOWN` 不会自动返回 `READY`，以免同一报文被重复投递。后端管理员核对 OutBox、单一窗口客户端和前置机账本后进行人工裁决：

- 确认从未投递：`DELIVERY_UNKNOWN -> READY`，允许重新拉取。
- 确认已经投递：`DELIVERY_UNKNOWN -> RECEIPT_PENDING`，继续等待回执。
- 原令牌仍匹配时，迟到的 `OUTBOX_DROPPED` 或有效回执仍可推进任务。

## 10. 重试与幂等策略

| 场景 | 前置机处理 |
|---|---|
| 连接失败、超时、连接被重置、响应无法解析 | 指数退避并加随机抖动；保留任务、账本和回执文件。 |
| HTTP `5xx`（不含明确的通道关闭语义） | 自动重试，持续失败写入 `lastError` 并告警。 |
| HTTP `503` + `1050000200` | 后端通道关闭；降低重试频率并告警，不拉取新任务，未上传回执必须保留。 |
| HTTP `401` + `1050000201` | 密钥无效；停止高频请求并告警，由管理员更换企业鉴权密钥。 |
| `1050000202` 任务不存在 | 不重试该状态回报，保留本地审计记录并告警。 |
| `1050000203` 状态冲突 | 不重复写 OutBox；核对本地账本、实例名和令牌，必要时由双方人工处理。 |
| `1050000204/205` 回执内容非法或过大 | 记为 `PERMANENT_REJECTED`，停止自动重试并告警；文件保留在 InBox。 |
| 请求参数校验失败 | 修复本地配置/程序后再请求，不应无限重试原请求。 |

推荐退避参数：首次 1 秒，按 2 倍增长，最大 60 秒，并加入 0～20% 随机抖动；鉴权失败和通道关闭使用至少 60 秒的低频探测。具体间隔可配置。

前置机必须持久化两类本地状态：

- 投递账本/写前日志：以 `taskId + xmlSha256` 唯一，至少记录 `PREPARED`、`DELIVERED` 状态，以及 `clientSeqNo`、实际文件名、临时文件名、目标目录、首次投递时间和当时的 `dispatchToken`。状态和关键字段更新需要持久化到磁盘，不能只留在内存。
- 回执处理账本：以 `xmlSha256` 唯一，记录文件发现、上传重试、后端确认、未匹配和永久拒绝状态。进程重启后必须能继续，且不得重新上传已确认内容。

## 11. 错误码

| HTTP | `code` | 含义 | 是否自动重试 |
|---|---:|---|---|
| 503 | `1050000200` | 前置机通道关闭 | 低频探测并告警 |
| 401 | `1050000201` | 企业鉴权密钥无效 | 否，等待更换配置 |
| 通常 200 | `1050000202` | 前置机任务不存在 | 否 |
| 通常 200 | `1050000203` | 前置机任务状态冲突 | 否，先核查状态和账本 |
| 通常 200 | `1050000204` | 回执 XML/Base64 无效或缺少 `ClientSeqNo` | 否 |
| 通常 200 | `1050000205` | 回执解码后超过大小限制 | 否 |
| 通常 200 | `400` | 请求字段、类型或格式校验失败 | 修复请求后再试 |
| 5xx | `500` 或其他 | 后端临时异常 | 是 |

租户停用或过期时，后端返回 HTTP `401`。响应消息为“企业已停用或过期”，当前业务码为 `1050000200`。

## 13. 安全与日志要求

- 企业鉴权密钥只能保存于前置机受限配置或系统凭据存储中，文件 ACL 仅允许前置机服务账号读取。
- 日志、异常、监控、截图和工单中不得输出完整 `X-Agent-Key`；如需定位最多显示末 4 位。
- 不得记录完整 `decXmlBase64`、`receiptXmlBase64` 或解码后的 XML。日志只记录 `taskId`、`clientSeqNo`、文件名、SHA-256、状态和错误摘要。
- 后端四个接口已关闭请求体和响应体访问日志；前置机也必须遵守相同原则。
- 生产环境必须校验证书链和主机名，禁止长期关闭 TLS 校验。
- 配置、SQLite 账本以及 OutBox、InBox 目录应限制访问权限，并纳入磁盘容量监控；InBox 历史文件由客户现场按其制度清理。
- 密钥重置后旧密钥立即失效，前置机需要由管理员安全更新配置并重启/热加载。

## 14. 双方职责边界

| 本项目后端负责 | Windows 前置机负责 |
|---|---|
| 企业鉴权、租户识别与数据隔离 | 安全保存租户企业鉴权密钥 |
| 生成 DEC XML、`ClientSeqNo`、文件名和 SHA-256 | 拉取任务并 Base64 解码 |
| 任务原子抢占、分派令牌和租约 | 将所有 DEC 原样写入统一 OutBox，并轮询统一 InBox |
| 回执 XML 安全解析、匹配、去重和留档 | 临时文件写入、双重租约检查和原子 rename |
| 暂存主状态更新与历史记录 | SQLite 投递账本和回执处理账本 |
| 租约过期检测、告警和后台人工裁决接口 | 状态回报、回执原文上传和离线重试 |
| 前置机实例心跳记录 | 本地目录健康检查和心跳上报 |
| 提供联调环境、测试租户和 `sk-...` 密钥 | Windows 服务安装、自启、升级和现场目录适配 |

前置机不负责解析海关业务回执、不生成 `ClientSeqNo`、不判断租户、不处理租户类型默认值，也不调用后端管理端的人工裁决接口。

## 15. 联调与验收清单

### 15.1 基础与鉴权

- [ ] 正确密钥可调用四个接口，且只能获取本租户任务。
- [ ] 缺少、错误和已重置的密钥均被拒绝。
- [ ] 租户停用/过期和后端总开关关闭时，前置机能够低频探测并明确告警。
- [ ] 日志中不存在完整密钥、DEC XML、回执 XML 或对应 Base64。

### 15.2 任务投递

- [ ] `export`、`import`、`9610` 均进入统一 OutBox，生成的 DEC 分别携带正确的 `IEFlag`。
- [ ] 每个拉取任务均返回 `businessModuleCode=DECCUS001`；前置机能据此选择“货物申报（报关单暂存）”模块。
- [ ] 前置机收到不支持的业务模块代码时停止投递并告警，不回退到 `OTHERS`。
- [ ] 正常任务按“临时文件 -> 双检租约 -> `PREPARED` 写前落盘 -> 原子 rename -> `DELIVERED` 落盘 -> 状态回报”执行。
- [ ] 同一 `taskId + xmlSha256` 再次出现时不重复写 OutBox，只回报当前分派状态。
- [ ] 状态回报超时后只重试回报，不重复写文件。
- [ ] 错误实例名、旧 `dispatchToken` 和非法状态能被识别并停止自动处理。
- [ ] 进程在写临时文件、rename、记账、回报前后分别崩溃时，重启后不会重复投递。

### 15.3 回执

- [ ] 正常 `DecImportResponse` 成功回执更新为 `SUCCESS`。
- [ ] `ResponseCode != 0` 的暂存回执更新为 `FAILED` 并保留错误信息。
- [ ] 同一回执重复上传返回 `duplicate = true`，不重复推进状态。
- [ ] 回执先于 `OUTBOX_DROPPED` 到达时仍能正确匹配任务。
- [ ] 无匹配任务、未知回执类型、非法 XML、缺少 `ClientSeqNo` 和超大文件均按约定处理。
- [ ] 服务端确认后 InBox 文件保持原位，后续扫描通过 SQLite 账本跳过，不再重复上传。
- [ ] 同一内容改名或复制后不会重复上传；同名文件内容变化后能够按新 SHA-256 重新处理。
- [ ] 未匹配回执记为 `ACKED_UNMATCHED`，非法或超大回执记为 `PERMANENT_REJECTED`，均只告警一次且不会高频重传。
- [ ] 断网和前置机重启后，未确认回执不会丢失且能继续上传。

### 15.4 心跳与异常恢复

- [ ] 心跳能展示实例名、版本、IP 和统一 OutBox/InBox 健康状态。
- [ ] 停止前置机超过 3 分钟能触发后端超时告警。
- [ ] 模拟 pull 响应丢失或租约到期，任务进入 `DELIVERY_UNKNOWN` 且不会自动重投。
- [ ] 后端人工确认未投递后，任务可重新拉取，前置机账本仍能阻止误重复投递。
- [ ] 磁盘满、OutBox 不可写、InBox 不可读、证书异常和密钥失效均有清晰告警。

联调完成的最低标准是：正常链路可闭环、网络中断可恢复、进程崩溃不重复投递、回执不丢失、租约不被绕过、密钥和 XML 不进入日志。
